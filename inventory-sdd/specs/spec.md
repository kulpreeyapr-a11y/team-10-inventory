# Spec: ฟีเจอร์แจ้งเตือนสต็อกต่ำ และรายงานมูลค่าสต็อก

## 1. เป้าหมาย (Goal)
เพิ่มความสามารถให้ระบบ inventory แจ้งเตือนผู้จัดการเมื่อสินค้าใดต่ำกว่า threshold และให้ผู้จัดการดูรายงานมูลค่าสต็อกแยกตามหมวดหมู่ได้

## 2. User Story
| รหัส | User Story |
|---|---|
| US-01 | As a พนักงานคลังสินค้า, I want บันทึกการรับ/จ่ายสินค้าพร้อมอัปเดตสต็อกทันที, so that สต็อกในระบบสะท้อนจำนวนจริง |
| US-02 | As a ผู้จัดการ, I want รับการแจ้งเตือนทันทีเมื่อสินค้าใดต่ำกว่า threshold, so that สั่งซื้อได้ก่อนของหมด |
| US-03 | As a ผู้จัดการ, I want ดูมูลค่ารวมของสต็อกแยกตามหมวดหมู่, so that ตัดสินใจด้านการเงินได้ |
| US-04 | As a ผู้จัดการ, I want ตั้งค่า threshold รายสินค้าได้, so that กำหนดจุดเตือนภัยที่เหมาะสมกับสินค้าแต่ละชนิด |
| US-05 | As a ผู้จัดการ, I want เลือกช่องทางแจ้งเตือน email หรือ sms ได้, so that รับข้อความผ่านช่องทางที่สะดวก |

  ## 3. Acceptance Criteria (Given-When-Then)
  ### AC ของ US-01 (บันทึกรับ/จ่ายสินค้า)
```gherkin
  Scenario: บันทึกการจ่ายสินค้าสำเร็จ
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 30 เมตร
  When พนักงานบันทึกจ่ายออก 10 เมตร
  Then สต็อกคงเหลืออัปเดตเป็น 20 เมตร

  Scenario: ปฏิเสธการจ่ายสินค้าเมื่อสต็อกไม่พอ
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 5 เมตร
  When พนักงานบันทึกจ่ายออก 10 เมตร
  Then ระบบปฏิเสธการทำรายการพร้อมแสดงข้อผิดพลาด "สต็อกไม่เพียงพอ"
  And สต็อกคงเหลือยังคงเป็น 5 เมตรเท่าเดิม

  Scenario: บันทึกรับสินค้าเข้าคลังสำเร็จ
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 10 เมตร
  When พนักงานบันทึกรับเข้า 20 เมตร
  Then สต็อกคงเหลืออัปเดตเป็น 30 เมตร
```
  ### AC ของ US-02 (แจ้งเตือนสต็อกต่ำ)
  Scenario: จ่ายสินค้าจนสต็อกต่ำกว่า threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 8 เมตร
  Then สต็อกคงเหลือ 12 เมตร
  And ระบบส่งการแจ้งเตือนถึงผู้จัดการว่าสต็อกต่ำ

  Scenario: จ่ายสินค้าโดยสต็อกยังสูงกว่า threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 50 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 10 เมตร
  Then สต็อกคงเหลือ 40 เมตร
  And ระบบไม่ส่งการแจ้งเตือน

  Scenario: จ่ายสินค้าจนสต็อกเท่ากับ threshold พอดี (Edge Case)
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 5 เมตร
  Then สต็อกคงเหลือ 15 เมตร
  And ระบบไม่ส่งการแจ้งเตือน

  ### AC ของ US-03 (รายงานมูลค่าสต็อก)
  Scenario: คำนวณมูลค่าสต็อกรวมแยกตามหมวดหมู่ถูกต้อง
  Given มีสินค้าหมวด "ไฟฟ้า" ชื่อ "สายไฟ" จำนวน 10 ชิ้น ราคาชิ้นละ 5,000 บาท
  And มีสินค้าหมวด "ประปา" ชื่อ "ท่อ PVC" จำนวน 100 ท่อน ราคาท่อนละ 300 บาท
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then ระบบแสดงมูลค่าหมวด "ไฟฟ้า" เท่ากับ 50,000 บาท
  And แสดงมูลค่าหมวด "ประปา" เท่ากับ 30,000 บาท
  And แสดงมูลค่ารวมทั้งหมดเท่ากับ 80,000 บาท

  Scenario: เรียกดูรายงานเมื่อไม่มีสินค้าในระบบ
  Given ไม่พบรายการสินค้าในระบบ
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then ระบบแสดงมูลค่ารวมเท่ากับ 0 บาท

  ### AC ของ US-04 และ US-05 (ตั้งค่า Threshold และช่องทางแจ้งเตือน)
  Scenario: ตั้งค่า threshold รายสินค้า
  Given สินค้า "ท่อ PVC" มี threshold เดิมเท่ากับ 10
  When ผู้จัดการแก้ไข threshold ของ "ท่อ PVC" เป็น 25
  Then threshold ของ "ท่อ PVC" อัปเดตเป็น 25

  Scenario: ส่งแจ้งเตือนตามช่องทางที่เลือก (Email และ SMS)
  Given ผู้จัดการเลือกช่องทางแจ้งเตือนเป็น "Email" และ "SMS"
  When สินค้า "สายไฟ" มีสต็อกต่ำกว่า threshold
  Then ระบบส่งข้อความแจ้งเตือนไปที่ Email และ SMS ของผู้จัดการ

## 4. In Scope / Out of Scope
**In Scope:** บันทึกรับ/จ่าย + อัปเดตสต็อกใน memory, แจ้งเตือน email/sms (print แทนส่งจริง), รายงานมูลค่าแยกหมวด, กำหนด threshold รายสินค้าผ่าน parameter/code
**Out of Scope:** ส่ง email/sms ผ่านเซิร์ฟเวอร์จริง, ระบบ login/สิทธิ์, ฐานข้อมูลถาวร, การตั้งค่าคอนฟิกผ่าน Web UI

## 5. Functional Requirements (FR)
| รหัส | ความต้องการ | จาก Story |
|---|---|---|
| FR-01 | ระบบต้องอัปเดตสต็อกทันทีหลังบันทึกรับ/จ่าย | US-01 |
| FR-02 | ระบบต้องตรวจสต็อกก่อนจ่าย และปฏิเสธถ้าไม่พอ | US-01 |
| FR-03 | ระบบต้องแจ้งเตือนเมื่อสต็อกหลังจ่ายต่ำกว่า threshold | US-02 |
| FR-04 | ระบบต้องคำนวณและรายงานมูลค่าสต็อกแยกตามหมวดหมู่ได้ | US-03 |
| FR-05 | ระบบต้องอนุญาตให้ตั้งค่า threshold แยกตามรายสินค้าได้ | US-04 |
| FR-06 | ระบบต้องรองรับการส่งแจ้งเตือนผ่านช่องทาง Email และ SMS | US-05 |

## 6. Non-Functional Requirements (NFR)
| รหัส | มิติ | ความต้องการ (ต้องวัดได้) |
|---|---|---|
| NFR-01 | Performance | รายงานมูลค่าสต็อก 1,000 รายการเสร็จภายใน 1 วินาที |
| NFR-02 | Maintainability | เพิ่มช่องทางแจ้งเตือนใหม่ได้โดยไม่แก้ business logic เดิม |
| NFR-03 | Reliability | หากการส่งแจ้งเตือนล้มเหลว ระบบต้องยังคงอัปเดตสต็อกได้สำเร็จ |

## 7. Design Notes
- การแจ้งเตือนต้องแยกออกจาก business logic ของสต็อก
- คาดว่าจะมีหลายช่องทางแจ้งเตือน ควรออกแบบให้เพิ่มได้ง่าย

## 8. ผลการตรวจ Acceptance Criteria ด้วย MASTER Checklist

| AC ข้อที่ | Story | M | A | S | T | E | R | สรุปผลการประเมิน |
|---|---|:---:|:---:|:---:|:---:|:---:|:---:|---|
| **AC-01** | US-01 (บันทึกจ่ายสำเร็จ) |  |  |  |  |  |  | **ผ่าน:** ระบุตัวเลขชัดเจน (30, 10, 20) วัดผลได้ทันที |
| **AC-02** | US-01 (สต็อกไม่พอ) |  |  |  |  |  |  | **ผ่าน:** มีการ Return Error Message ชัดเจน ตรวจสอบผลลัพธ์ได้ |
| **AC-03** | US-02 (ต่ำกว่า threshold) |  |  |  |  |  |  | **ผ่าน:** ตัวเลขสต็อกหลังตัดข้ามเกณฑ์ เตือนออกภายนอกชัดเจน |
| **AC-04** | US-02 (สูงกว่า threshold) |  |  |  |  |  |  | **ผ่าน:** มี Negative Scenario ทดสอบกรณีไม่ส่งเตือนได้ |
| **AC-05** | US-03 (รายงานมีสินค้า) |  |  |  |  |  |  | **ผ่าน:** คำนวณมูลค่ารวม (80,000) ได้ถูกต้องตามสูตร |
| **AC-06** | US-03 (รายงานไม่มีสินค้า) |  |  |  |  |  |  | **ผ่าน:** มี Edge Case กรณีสินค้าเป็น 0 บาท ครบถ้วน |

**คำอธิบายเกณฑ์ MASTER:**
- **M (Measurable):** ตัวเลข ผลลัพธ์ และสถานะวัดผลได้ชัดเจน
- **A (Achievable):** ทำสำเร็จได้ในขอบเขต Memory/Console ของ Lab
- **S (Specific):** ระบุชื่อสินค้า และจำนวนชัดเจน ไม่กำกวม
- **T (Testable):** เขียน Test Script (PyTest/Unit Test) ได้ทันที
- **E (External observable):** สังเกตผลลัพธ์ผ่าน Return value หรือ Console Print ได้
- **R (Relevant):** ตรงกับคุณค่า/ประโยชน์ที่ User ใน Story ต้องการ
